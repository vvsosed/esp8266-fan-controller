# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Single-sketch Arduino firmware for an ESP8266 (Wemos D1 mini / NodeMCU) that drives three 4-pin PWM PC fans from one DS1820 temperature reading (cutting their 12 V at 0 %), prints each fan's RPM over serial, serves a status page over Wi-Fi, shares the fan curve and readings over MQTT, counts its own boots and crashes, and stamps its serial log with the boot number, uptime and network time. There is no build system, test suite or CI: verification is "it compiles" plus reading the serial output and the status page on real hardware.

The Arduino IDE requires the sketch file name to match its folder, so `fan_controller.ino` cannot be renamed or moved without renaming the directory too.

## Commands

```bash
./build.sh                                # compile (args pass through to arduino-cli compile; add -v for full output)
./build.sh --upload                       # compile + flash
arduino-cli upload .                      # flash last build
arduino-cli monitor -p $PORT --config baudrate=115200
./build.sh -e                             # export .bin to ./build/<fqbn>/
./build.sh --clean
arduino-cli board list                    # find $PORT
```

Build through `./build.sh`, not bare `arduino-cli compile`. It writes the gitignored `git_hash.h` (`#define GIT_HASH "<git describe --always --dirty>"`) and then execs `arduino-cli compile "$@" .`. The sketch falls back to `GIT_HASH "unknown"` via `__has_include` when the header is absent. Don't rename it to `version.h`: the ESP8266 SDK has its own `version.h` on the include path, which wins `__has_include`, leaving `GIT_HASH` undefined. `FW_VERSION` at the top of the sketch is bumped by hand. Both appear in the status page footer.

These flagless forms depend on a `sketch.yaml` created by `arduino-cli board attach -p $PORT -b $FQBN .`. **`sketch.yaml` is not in the repo**, so on a fresh checkout either run `board attach` first or pass `-b $FQBN` (and `-p $PORT` for upload) on every command. Typical FQBN: `esp8266:esp8266:d1_mini:xtal=160,baud=921600`.

Prerequisites (once per machine): ESP8266 core from `https://arduino.esp8266.com/stable/package_esp8266com_index.json`, plus `arduino-cli lib install OneWire DallasTemperature WiFiManager@2.0.17 PubSubClient@2.8.0` (tzapu; knolleary). The serial monitor holds the port — close it before uploading. README.md has the full Manjaro/Arch setup and a troubleshooting table.

## Architecture

Everything lives in `fan_controller.ino`: a 1-second cooperative loop (early-returns until 1000 ms have elapsed). It blocks only in the few places listed below: Wi-Fi scans and saves, and MQTT connects.

- **Index-parallel arrays.** `PWM_PIN[i]`, `TACH_PIN[i]`, `pulses[i]` and `isr[i]` all describe fan `i`. Adding or reordering a fan means touching all four, including the hand-written `t0/t1/t2` ISRs, which exist one-per-fan because `attachInterrupt` takes no argument.
- **PWM duty is inverted** (`255 - pct*255/100`). Each GPIO drives an NPN/MOSFET open-drain stage, mimicking a motherboard, so GPIO high pulls the fan's PWM line low. A fan wired directly to a GPIO instead needs the non-inverted form.
- **Failure modes default to full speed.** A missing sensor (`DEVICE_DISCONNECTED_C`) forces `PCT_FAILSAFE` (100 %, deliberately separate from the user-settable `curve.pctMax`), and an undriven fan PWM pin is pulled up internally by the fan, so fans also run full-speed during boot and reset. The 12 V switch fails on in the same way: the core's `resetPins()` leaves GPIO16 as an input until `setup()` drives it, and a 10 kΩ pull-up keeps the switch on meanwhile. The one gap is the board losing its own power, which takes the pull-up's 3.3 V with it.
- **0 % duty cuts the fans' 12 V** via `POWER_PIN` (GPIO16/D0 → NPN → high-side P-MOSFET; HIGH = on), because most fans only drop to a minimum speed at 0 % PWM. `setFanPower()` turns it back on the first cycle above 0 %, but off only after the curve has given 0 % even `POWER_HYST_C` warmer for `POWER_OFF_DELAY_S` consecutive cycles. Keep both guards: `curvePct()` works in whole degrees (`map((long)t, …)`, which rounds in core 3.1.2), so with `pctMin` 0 the duty steps between 0 and >0 at one whole degree, and sensor noise there would toggle the rail. A failed read forces the rail on for that cycle only, without touching the hysteresis state, so a glitch costs 1 s instead of restarting the off-delay. While the rail is cut, `loop()` writes 100 % (GPIO low) to the PWM pins, so their transistors don't sit saturated for nothing. `fanPower` feeds `"pwr"` in `/status.json`.
- **Temperature is one cycle stale by design.** `setWaitForConversion(false)` plus "read, then request next" keeps the 750 ms DS1820 conversion off the loop.
- **A failed temperature read is retried once.** On the ESP8266, OneWire's bit-timing functions run from flash (its `IRAM_ATTR` placement is ESP32-only). Serving a web page evicts them from the instruction cache, and a cache miss mid-slot blows the DS18B20's 15 µs read window, so ~1 in 3 reads after a page load returned -127. The failed try reloads the cache and the retry succeeds. Don't remove it as redundant.
- **RPM = pulses × 30000 / dt_ms** (2 pulses per revolution). `dt` is measured, not assumed, so the reading stays correct if a cycle runs long. Counters are snapshot-and-cleared inside `noInterrupts()`.
- **The fan curve** is the `curve` struct (`tLow`/`tHigh` °C, `pctMin`/`pctMax` %), linearly mapped and clamped. It is set from the status page (`POST /curve`) or over MQTT and persisted with the core `EEPROM` library (one flash sector, written only on Save; a magic word guards the layout, so bump `CURVE_MAGIC` if `Curve` changes). `DEFAULT_CURVE` is used on first boot, on a bad/missing EEPROM record, and by the page's Defaults button. Every curve, loaded or posted, goes through `validCurve()`; its `tLow < tHigh` rule is what keeps `map()` from dividing by zero, and `pctMax > 0` keeps a 0 → 0 % curve from cutting the fans' 12 V at every temperature.
- **Wi-Fi is WiFiManager in non-blocking mode.** `wm.process()` and `MDNS.update()` sit *above* the 1 s gate in `loop()` so they run every pass; fan regulation continues while the setup AP is up. The longest block is `autoConnect()` in `setup()` (≤ `CONNECT_TIMEOUT_S`, fans already at `PCT_FAILSAFE`). `/wifi` scans, network saves and MQTT connects (below) also stall the loop for a few seconds, which is harmless because PWM is timer-driven and `dt` is measured.
  - There is one web server: WiFiManager's `wm.server`. It is used both for the setup AP (config portal) and on the LAN (`startWebPortal()`, started by the edge check in `loop()` once connected). Our routes go in `addRoutes()` via `setWebServerCallback`, which WiFiManager calls *before* registering its own, so our `/` shadows its menu. `handleRoot()` redirects to `/wifi` while `wm.getConfigPortalActive()` (setup AP) and otherwise sends a static page (the curve form) whose script polls `/status.json` (`handleStatus()` → `statusJson()`: the `last*` globals the 1 s block fills, plus uptime, the clock and the boot counter; `STATUS_N` sizes its buffers and is the only limit, because each part is written straight into the caller's buffer). The page must not auto-reload, or it would wipe the form while the user types. `/status.json` is named so because WiFiManager already owns `/status`.
  - The page is streamed in parts: `PAGE_HEAD` + `hostname` (the `<title>`) + `PAGE_TOP` (PROGMEM, split at the title so it stays in the head), two `snprintf`'d chunks sharing one 1 KB buffer (the curve form, then the broker form + footer), and `PAGE_SCRIPT` (PROGMEM, the status poll plus a hand-drawn canvas chart; no external JS, so it works without internet). `%` is literal in the PROGMEM parts; only the `snprintf` part needs `%%`. Responses use `setContentLength(CONTENT_LENGTH_UNKNOWN)`: chunked on HTTP/1.1, close-delimited on HTTP/1.0. Don't switch to `chunkedResponseModeStart()`, which refuses HTTP/1.0 clients.
  - The graph history is a RAM ring buffer `hist[HIST_N]` (360 × 10-cycle averages ≈ 1 h; `INT16_MIN` = no reading). `histAdd()` runs once per 1 s cycle, so the cadence counts cycles, not wall time. `/history.json` streams it in small pieces; don't build it in one buffer.
  - WiFiManager's own pages get `WM_HEAD` via `setCustomHeadElement()`. It only acts on a successful browser OTA (`/update` → POST `/u`): it polls `/status.json` until the rebooted board answers, then `location.replace('/')`, so Back can't re-post the firmware. It lands on every WiFiManager page, so keep the path + `.msg.S` guard. Keep it a RAM string too, since WiFiManager appends it as a plain `const char*`.
  - Each board names itself `fan-controller-<chip id>` (`hostname`, built in `setup()` from `ESP.getChipId()`). It is the DHCP name, the mDNS name and the setup AP SSID alike, so several boards can share a network. Don't make it a fixed constant again: two boards would clash on mDNS, and with no conflict callback set the core just drops the name.
  - Portal timeout (`PORTAL_TIMEOUT_S`) is set only when a network is already saved, and its callback restarts the board to retry it. First-time setup never times out.
  - Double reset uses RTC user memory block 0 (survives RST, not power loss) and only counts `REASON_EXT_SYS_RST`, so crashes and `ESP.restart()` don't trigger it. No GPIOs are involved.
- **MQTT is PubSubClient, off until a broker is saved.** The broker (`MqttCfg`) is entered on the status page (`POST /mqtt`, `handleMqtt()`) and stored as a second EEPROM record at the fixed offset `MQTT_AT` (64), with its own `MQTT_MAGIC`, so a change to `Curve` moves neither record. `saveMqtt()` zero-fills the record, padding included, and `handleMqtt()` `strncpy`s each field, which zero-fills the rest of the field. So an unchanged Save writes nothing, and no tail of an older, longer password stays in flash. A blank password field keeps the saved password only while the host and user stay the same, so a changed host never receives the old one. Host and user are echoed into the form's `value='…'`, so `handleMqtt()` restricts their characters instead of escaping them.
  - Topics hang off `hostname`: `ramp` `{"low","high"}` and `duty` `{"min","max"}` (retained), a `…/set` for each, `status` (the live part of `/status.json`, `statusJson(…, JSON_LIVE)`, every `MQTT_STATUS_S` cycles, not retained), `boot` (`JSON_BOOT`: boots, `booted`, reset and last crash; retained; published at each connect, and once more after the first sync to add `booted`) and `online` (retained, published last so whoever reacts to it finds the rest current; last will `offline`).
  - `onMqtt()` merges the keys given into a copy of `curve` and applies it with `applyCurve()`, the same path `handleCurve()` uses: set, save, print, publish. A set is all or nothing. `jsonInt()` returns -1 for a key that is present but isn't a whole number, and one such key, a merged curve that fails `validCurve()`, or a payload over 127 bytes rejects the whole set. It republishes `ramp`/`duty` whether or not it applied them, so the retained topics always match the curve in force. It copies the payload before anything else: PubSubClient has one buffer, and a publish from inside the callback overwrites it. `jsonInt()` is a deliberately tiny reader for these flat payloads, to avoid pulling in ArduinoJson.
  - `mqttProcess()` sits above the 1 s gate with `wm.process()`. A connect is its only blocking call. Failed tries back off from `MQTT_RETRY_MIN_S` to `MQTT_RETRY_MAX_S` (30 s → 5 min). `mqttRetryS` = 0 means try now: at boot, after a form save, and after a drop from a good connection. The wait is an unsigned `millis() - mqttLastTry` difference; a deadline compared with a signed cast stopped retrying after a connection had lasted 2^31 ms (~25 days). `publishStatus()` checks `WiFi.isConnected()` itself, because it runs from the 1 s block, not from `mqttProcess()`, and a write to a dead link's socket blocks. `net.setTimeout(2000)` and `setSocketTimeout(2)` cap a dead broker at ~6 s per try; the defaults (5 s DNS + 5 s TCP + 15 s CONNACK) would stall the loop for up to 25 s. A `.local` broker never resolves: lwIP's DNS doesn't do mDNS. `setBufferSize(STATUS_N + 64)` keeps every packet (5 B header + 2 B length + topic + payload) inside PubSubClient's buffer. Past it, `publish()` just returns false, and an incoming set is dropped before `onMqtt()` can log and answer it. The buffer would hold even both `statusJson()` parts in one message (266 B), so either part has room to grow; keep that true when adding a field.
  - `handleMqtt()` publishes `offline` itself before `disconnect()`, because a clean disconnect makes the broker drop the will.
  - `mqtt-broker/` is a throwaway Mosquitto image for testing (`docker build -t fan-mqtt mqtt-broker`; README has the run lines). Its `entrypoint.sh` writes the config on each start: `listener 1883` on all interfaces (Mosquitto 2 serves only localhost without one), anonymous unless `MQTT_USER` and `MQTT_PASS` are both set. The board must be given the PC's LAN IP, not `localhost`.
- **Boots and crashes are counted** for stability monitoring: `countBoot()` runs early in `setup()`, right after the pins, so every log line has the boot number. The result is shown on the page's last two lines and as `up`/`boots`/`booted`/`reset`/`crashes`/`crash` in `statusJson()` (over MQTT, `up` is in `status` and the rest in `boot`).
  - The count is an append-only log of 24-byte `BootRec`s in two flash sectors of its own, the last two of the filesystem area (`FS_PHYS_ADDR`/`FS_PHYS_SIZE` from `flash_hal.h`, which `Arduino.h` only includes on flash-map builds). The sketch has no filesystem, and OTA writes end at `FS_start`. Each boot programs one record into erased flash, with no erase. When a sector fills, the other one is erased and the log moves there, so each sector is erased once per 2 × `LOG_N` (340) boots. The current count is the valid record with the most boots in either sector. So a power cut during a write or an erase loses that boot only, and a torn erase is simply redone on the next boot. The next write goes to the first fully erased slot after the newest record, which skips any torn slot. Don't move the count into the EEPROM sector: every update would erase that sector, so restart loops would wear it and a power cut would wipe the curve and broker settings.
  - Each record also carries the last crash forward (`crashAt` UTC s, 0 = unknown; `crashUp` s; `crashWhy`, an index into `RESET_NAME`), so it outlives later boots and power cuts. `crashWhy` is stored in flash, so `RESET_NAME` is append-only. Bump `BOOTS_MAGIC` if `BootRec` changes.
  - `recCheck()` is a mixing hash (each word through murmur3's finalizer), not an XOR. A torn write leaves an arbitrary subset of bits unprogrammed, and an XOR check passes when the same bit is missing from a field and `check`. A host test found that in about half of such tears, which made the record valid with an inflated count. `recValid()` also rejects an erased slot explicitly.
  - With a layout that has no filesystem area (`FS:none`), the counter is off and shows this boot only.
  - Crashes come from `custom_crash_callback()`, which overrides the core's weak hook. The core calls it for exceptions, soft WDT and panics (abort, assert, out-of-memory `new`) just before restarting. It stores the reason it is given in RTC user memory (`CrashRtc`, block `CRASH_RTC` = 32, plus a magic because RTC holds random bits after power-on) by direct `RTC_USER_MEM` stores, and ignores `REASON_DEFAULT_RST`, which is the SDK restarting itself. The crash's time and uptime come from `rtcBeat()`, which writes `at`/`up`/magic into the same record every 1 s cycle, so they also cover the hardware WDT. `whyBoot()` re-arms the record at boot as `{0, magic, 0, 0}` instead of zeroing it. So a crash before the first beat reads as up 0 with no time, and a valid magic tells the boot line how long the previous run lasted. `whyBoot()` counts a crash only from that record, or from reason 1 (the hardware WDT, which skips the hook). It doesn't trust reasons 2/3 alone: after an exception or soft WDT the SDK keeps reporting that reason for later plain restarts, so those boots are named `restart`.
  - Keep RTC data at block 32 or above: an OTA update writes the bootloader's command into blocks 0–31 (the double-reset flag at block 0 sits there too, which is harmless for a flag that only needs to survive one RST).
  - `BootRec` and `CrashRtc` are defined in the config section at the top, not with the counter code, because arduino-cli inserts the sketch's function prototypes just above the tach ISRs. Any type used in a function signature must be declared above that point.
- **Two kinds of time.** The monotone one is the boot number plus `micros64()` uptime: it never jumps, works without network, and orders events across boots. The clock comes from SNTP and is for the log, the page and the JSON only. Nothing that controls the fans may use it: control timing stays on `millis()`, because the clock jumps at the first sync and steps at each hourly correction.
  - `startLan()` calls `configTime(TIMEZONE, NTP_SERVER)`, which (re)starts SNTP once the LAN is up. Don't move it into `setup()`: before Wi-Fi is up the first request fails, and lwIP retries only after 15 s, doubling to 150 s. `setup()` only sets `setTZ()` (so the boot line can print a crash time) and `settimeofday_cb(onTimeSync)`, which on the first sync sets `timeSynced` and `bootedAt` (`time()` − uptime, kept so `booted` doesn't wobble by a second between publishes) and logs it. The core runs that callback as a recurrent scheduled function, so it can fire inside any `yield()` or `delay()`, even in the middle of a publish's TCP write. So it must not publish: it sets `bootDue`, and `mqttProcess()` sends `boot` from `loop()`. `publishBoot()` clears the flag before it publishes, so a sync during that publish's own yield still gets sent. Until then `time()` is just uptime, so everything checks `timeSynced`; `"time"` in the JSON is `null` without it.
  - `stamp()` starts every serial log line: `#<boot> +<s>.<ms> `, plus the local `%F %T` once synced. Call it before the first print of any new log line. WiFiManager's own `*wm:` lines stay unstamped. Uptime is split into seconds and milliseconds from `micros64()`, not `millis()`, which wraps after 49.7 days.
  - `TIMEZONE` is a POSIX TZ string (the core's `TZ.h` lists them). It affects serial only: the JSON carries UTC seconds, and the page's script shows them in the browser's local time.

## Hardware constraints that bind the code

`docs/esp8266-fan-controller-research.md` is the design rationale — read §4 (pin map) and §8 (caveats) before changing pins. The pin choices are forced, not stylistic:

- **GPIO15 (D8) must be low at boot**, so it is only usable as a PWM output *through a transistor*; a directly wired fan pulls it high and the board will not boot.
- **GPIO2 (D4) must be high at boot**, which the 1-Wire 4.7 kΩ pull-up satisfies — hence the DS1820 lives there, and tach lines must never go on GPIO0 or GPIO2.
- **GPIO16 (D0) has no interrupt support**, so it cannot carry a tach signal. It is the plain output for the 12 V switch. It has no internal pull-up, hence the external 10 kΩ.
- All 8 signals use the only unrestricted pins (GPIO4/5/12/13/14) plus GPIO15/GPIO2/GPIO16. The board is pin-full: further peripherals mean moving to an ESP32.
- Tach pull-ups go to **3.3 V only**, never 12 V. Fans need a separate 12 V supply with grounds tied common, switched **high-side** (a switched fan ground would float the tach/PWM lines toward 12 V).

Note: §7 of the research doc contains a copy of the firmware. `fan_controller.ino` is the source of truth; the doc copy may drift.

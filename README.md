# fan_controller

ESP8266 firmware that drives three 4-pin PWM PC fans from a DS1820 temperature reading, reports each fan's RPM over serial, serves a status page over Wi-Fi, and shares its fan curve and readings over MQTT.

Hardware design, wiring and parts list: see [`docs/esp8266-fan-controller-research.md`](docs/esp8266-fan-controller-research.md).

---

## Quick reference

Run all commands from inside the sketch folder.

| Task | Command |
|---|---|
| Compile | `./build.sh` |
| Compile + flash | `./build.sh --upload` |
| Flash last build | `arduino-cli upload .` |
| Serial monitor | `arduino-cli monitor -p $PORT --config baudrate=115200` |
| Export `.bin` to `./build` | `./build.sh -e` |
| Clean rebuild | `./build.sh --clean` |
| Find connected boards | `arduino-cli board list` |
| Update cores/libraries | `arduino-cli update && arduino-cli upgrade` |

These short forms work after the one-time `board attach` step in [Setup](#4-attach-board-and-port-to-the-sketch). Without it, add `-b $FQBN` (and `-p $PORT` for upload).

`./build.sh` writes the current git commit into `git_hash.h`, then runs `arduino-cli compile` with any extra arguments you give it. The commit shows in the status page footer. Plain `arduino-cli compile .` also builds, but the footer then shows `unknown`, or the commit from the last `./build.sh` run.

## Hardware summary

| Signal | GPIO | Board label | Notes |
|---|---|---|---|
| Fan 1 / 2 / 3 PWM | 12 / 13 / 15 | D6 / D7 / D8 | Through NPN/MOSFET open-drain (inverted in firmware) |
| Fan 1 / 2 / 3 tach | 5 / 4 / 14 | D1 / D2 / D5 | 10 kΩ pull-up to **3.3 V** |
| DS1820 data | 2 | D4 | 4.7 kΩ pull-up to 3.3 V |
| Fans' 12 V switch | 16 | D0 | NPN + P-MOSFET high-side switch, 10 kΩ pull-up to 3.3 V. High or undriven = fans powered |

Fans run on a separate 12 V supply, switched on and off by D0 ([wiring](docs/esp8266-fan-controller-research.md#5-wiring-per-channel)). All grounds must be common.

## Setup (once per machine, Manjaro / Arch)

### 1. Install Arduino CLI and get serial port access

```bash
sudo pacman -S arduino-cli
sudo usermod -aG uucp $USER   # log out and back in afterwards
groups                        # should now list uucp
```

### 2. Install the ESP8266 core

```bash
arduino-cli config init
arduino-cli config add board_manager.additional_urls \
  https://arduino.esp8266.com/stable/package_esp8266com_index.json
arduino-cli core update-index
arduino-cli core install esp8266:esp8266
```

### 3. Install libraries

```bash
arduino-cli lib install OneWire DallasTemperature WiFiManager@2.0.17 PubSubClient@2.8.0
```

### 4. Attach board and port to the sketch

Set the board and port for your hardware:

```bash
export FQBN=esp8266:esp8266:d1_mini:xtal=160,baud=921600   # NodeMCU: esp8266:esp8266:nodemcuv2:...
export PORT=/dev/ttyUSB0                                   # check with: arduino-cli board list
```

| FQBN option | Meaning |
|---|---|
| `xtal=160` | CPU at 160 MHz (smoother software PWM) |
| `baud=921600` | Upload speed; use `115200` if uploads fail |
| `wipe=all` | Erase the entire flash on upload (use only when needed) |

List every option your board supports:

```bash
arduino-cli board details -b esp8266:esp8266:d1_mini
```

Save board and port into `sketch.yaml` so later commands need no flags:

```bash
arduino-cli board attach -p $PORT -b $FQBN .
```

### 5. Resolve `.local` names

The board announces itself over mDNS. Linux resolves `.local` names only when the Avahi daemon runs and `nss-mdns` is hooked into name lookup. Manjaro usually ships both packages with the daemon disabled.

```bash
sudo pacman -S --needed avahi nss-mdns
grep '^hosts' /etc/nsswitch.conf      # must contain: mdns_minimal [NOTFOUND=return] before resolve
sudo systemctl enable --now avahi-daemon
getent hosts fan-controller-XXXXXX.local   # once the board is on Wi-Fi: prints its IP
avahi-browse -rt _http._tcp                # lists every board on the network with its name and IP
```

If the `hosts:` line lacks `mdns_minimal`, edit it to look like this:

```
hosts: mymachines mdns_minimal [NOTFOUND=return] resolve [!UNAVAIL=return] files myhostname dns
```

Run the `sudo` lines in a normal terminal. Claude Code's `!` prefix can't answer the password prompt.

## Everyday tasks

### Compile

```bash
./build.sh                       # add -v for full compiler output
```

The build summary at the end shows flash and RAM usage.

### Flash

```bash
./build.sh --upload              # compile and flash in one step
arduino-cli upload .             # flash the last build without recompiling
```

Close the serial monitor first, because it holds the port.

### Serial monitor

```bash
arduino-cli monitor -p $PORT --config baudrate=115200
```

Exit with `Ctrl+C`. Expected output, once per second:

```
Temp 27.4 °C -> 30 % | Fan1 840 RPM Fan2 812 RPM Fan3 865 RPM
```

A burst of garbage right after reset is normal: the ESP8266 bootloader prints at 74880 baud.

Lines starting with `*wm:` come from WiFiManager. Once the board joins your router it prints where to find the [status page](#wi-fi):

```
Web UI: http://192.168.1.42/  (http://fan-controller-1a2b3c.local/)
```

### Get the compiled binary

By default, builds go to the cache at `~/.cache/arduino/sketches/<HASH>/fan_controller.ino.bin` (older CLI versions use `/tmp/arduino/sketches/<HASH>/`).

```bash
./build.sh -e                             # copy binaries to ./build/<fqbn>/
./build.sh --output-dir ./out             # copy binaries to a directory of your choice
arduino-cli compile --show-properties . | grep '^build.path'   # print the cache path
```

To always export binaries:

```bash
arduino-cli config set sketch.always_export_binaries true
```

### Flash a `.bin` with esptool directly

This is useful for flashing a saved build without the sketch.

```bash
sudo pacman -S esptool
esptool.py --port $PORT --baud 460800 write_flash 0x0 build/*/fan_controller.ino.bin
```

### Flash over Wi-Fi from the browser

Once the board is on your network, it doesn't need the USB cable:

1. Run `./build.sh -e`. Commit first if you want a clean hash in the [footer](#status-page).
2. On the status page, open **Info / erase Wi-Fi** → **Update**, choose `build/esp8266.esp8266.d1_mini/fan_controller.ino.bin` and press **Update**.
3. The page says `Update successful. Device rebooting now...`, waits until the board answers again (about 20 s), then opens the status page. Check the version in the footer.

The fans run at 100 % during the reboot. The saved curve and Wi-Fi settings are kept. If the board isn't back within a minute, press RST once (twice opens the setup access point).

### Erase the flash completely

Use this before flashing if the board behaves oddly after flashing other firmware.

```bash
esptool.py --port $PORT erase_flash
# or, through Arduino CLI, during upload:
arduino-cli upload -b $FQBN,wipe=all -p $PORT .
```

### Identify the chip and flash size

```bash
esptool.py --port $PORT flash_id
```

### Change the fan curve

Use the form on the [status page](#status-page), or [MQTT](#mqtt): duty ramps linearly from the low % at the low temperature to the high % at the high temperature, and is clamped outside that range. **Save** applies it on the next 1 s cycle and stores it in flash, so it survives reboots. **Defaults** restores the values compiled into the firmware.

| Field | Default | Allowed |
|---|---|---|
| Ramp start / end (°C) | 21 / 30 | 0–100, start below end |
| Duty at start / end (%) | 20 / 100 | 0–100, start ≤ end, end at least 1 (0 → 0 % would keep the fans switched off) |

The defaults are `DEFAULT_CURVE` in `fan_controller.ino`:

```cpp
const Curve DEFAULT_CURVE = {21, 30, 20, 100};   // tLow °C, tHigh °C, pctMin %, pctMax %
```

Editing them only matters until a curve has been saved from the page; after that the saved curve wins until you press **Defaults** (or flash with `wipe=all`).

A missing sensor and the boot period always run the fans at 100 % (`PCT_FAILSAFE`), even if the curve's maximum is lower.

**Fans fully off.** Most fans don't stop at 0 % PWM; they drop to a minimum speed instead. So when the curve gives 0 %, the firmware switches off the fans' 12 V through D0:

- **When it happens:** set **Duty at start** to 0 %. The curve works in whole degrees and rounds, so the duty leaves 0 % at the first whole degree where it reaches 1 %. With ramp start 22 °C that's 23 °C. A very flat curve, rising less than ½ % per degree (say 22–80 °C → 0–20 %), leaves 0 % a degree or more later.
- **On:** the 12 V comes back on in the next 1 s cycle once the duty is above 0.
- **Off:** the temperature has to fall 0.5 °C below that point (`POWER_HYST_C`; below 22.5 °C in the example) and stay there for 10 s straight (`POWER_OFF_DELAY_S`). In between, the fans keep running at their minimum speed. Without this, sensor noise right at the threshold would switch the fans on and off.
- **Sensor glitch:** a failed reading runs the fans at 100 % for that one second only; then they're off again.

## Wi-Fi

Your network's name and password are never in the source. WiFiManager stores them in the ESP's own flash.

### First-time setup

1. Flash the board. With no network saved, it starts an access point named `fan-controller-XXXXXX`, where `XXXXXX` is its chip ID. The board keeps that name on your network too (`http://fan-controller-XXXXXX.local/`), so note it down. Every board gets its own name, so several can share one network.
2. Join it from a phone or laptop. The password is `AP_PASS` in `fan_controller.ino` (default `fancontrol`).
3. A setup page opens by itself (otherwise browse to `http://192.168.4.1/`). Pick your network, enter its password, Save.
4. The access point shuts down and the board joins your router. Serial prints the `Web UI:` line.

The fans keep following the temperature the whole time the access point is up.

### Status page

Open `http://fan-controller-XXXXXX.local/`, the same name as the setup access point (needs [mDNS on your PC](#5-resolve-local-names)), or the IP from serial. The page title and footer show the board's name. It shows the temperature, fan duty and each fan's RPM, updating every 2 s, a graph of the last hour, the [fan curve](#change-the-fan-curve) form, the [MQTT](#mqtt) broker settings, and links to the pages below. When the 12 V is [switched off](#change-the-fan-curve), the status line says `fans off`. The last line shows the [uptime, boots and crashes](#uptime-boots-and-crashes).

**The graph:**
- Temperature (red, left °C axis) and duty (blue, right % axis), as 10-second averages.
- Dashed lines mark the curve's ramp start and end temperatures.
- Gaps mean the sensor wasn't read.
- The history is kept in the board's RAM, so it starts empty after every reboot or flash.
- Inside the ramp, duty follows temperature linearly, so the two lines often lie on top of each other. They separate where the duty is clamped at its minimum or maximum.

| Page | Use |
|---|---|
| `/history.json` | The graph data, oldest first: `{"step":10,"tl":21,"th":30,"t":[21.3,null,…],"d":[20,100,…]}` (`null` = no reading in that interval) |
| `/status.json` | The live numbers as JSON, e.g. `{"t":21.3,"pct":34,"pwr":1,"rpm":[600,630,660],"up":273600,"boots":14,"crashes":1,"reset":"power on"}` (`t` is `null` when the sensor is missing; `pwr` is 0 while the fans' 12 V is off; the rest is [uptime, boots and crashes](#uptime-boots-and-crashes)) |
| `/wifi` | Switch to a different network |
| `/info` | Chip details, and **Erase WiFi config** to forget the network (the board reboots into setup) |
| `/update` | Upload new firmware ([Flash over Wi-Fi](#flash-over-wi-fi-from-the-browser)) |

The footer shows what's running, e.g. `Firmware v0.0.1 · 37454aa`:

- **The version** is `FW_VERSION` at the top of `fan_controller.ino`. Bump it by hand when you release.
- **The commit** comes from `./build.sh`. A `-dirty` suffix means the build included uncommitted changes. To show a clean hash, commit first and then flash.

### Uptime, boots and crashes

To watch how stable the board is, the status page's last line shows e.g. `Up 3 d 04:12 · boots 14 · crashes 1 · last reset: power on`. [`/status.json`](#status-page) and the [MQTT](#mqtt) `status` topic carry the same as `up` (seconds since this start), `boots`, `crashes` and `reset`. Serial prints them at boot: `Boot 14, 1 crashes; this one: power on`.

- **boots** counts every start, this one included: power-ons, resets, firmware updates and crashes. Counting begins with the first firmware that has the counter. Only [erasing the flash completely](#erase-the-flash-completely) sets it back to 0.
- **crashes** counts the starts that followed a crash. This is the number to watch.
- **last reset** says why this start happened:

| `reset` | Cause |
|---|---|
| `power on` | The board got power. One that nobody caused means the supply dropped out |
| `reset pin` | The RST button, or a USB serial upload |
| `restart` | The firmware restarted itself: after a [firmware update over Wi-Fi](#flash-over-wi-fi-from-the-browser), when the setup access point [timed out](#getting-back-into-setup), or after **Erase WiFi config** |
| `exception` | Crash: the program hit a CPU exception, e.g. a bad pointer |
| `software watchdog`, `hardware watchdog` | Crash: the program got stuck |
| `panic` | Crash: abort, failed assert, or out of memory |

**Where the count is kept.** Each start adds a small record to a log in two flash sectors of their own, at the end of the 2 MB filesystem area. This firmware has no filesystem, and firmware updates don't write there. The fan curve and broker settings live elsewhere and are still written only when you save them.

- **Wear:** a record goes into erased flash, so most starts erase nothing. A sector is erased once every 341 starts. Even a crash every 5 s would erase each sector only about once an hour, years before typical flash (100,000 erases) wears out.
- **Power cuts:** a power cut while a record is being written loses that one start, nothing more.
- **Other flash layouts:** the counter needs the board's default layout, `4MB (FS:2MB …)`. Built with `FS:none`, it shows only the current start (`boots 1`), and serial says `Boot counter off`. If you ever add a filesystem to this firmware, keep it clear of its last two sectors.

**Watching it over MQTT.** A rising `crashes` means a crash; a falling `up` or a rising `boots` means some restart.

**Finding the cause of a crash.** Serial prints the crash before the board restarts: `Exception (n)`, `Soft WDT reset`, `Panic …` or `Abort called`, then a stack dump between `>>>stack>>>` and `<<<stack<<<`. Turn the code addresses (`40xxxxxx`) into source lines with the `.elf` of the same build (`./build.sh -e` exports it):

```bash
~/.arduino15/packages/esp8266/tools/xtensa-lx106-elf-gcc/*/bin/xtensa-lx106-elf-addr2line -pfiaC \
  -e build/esp8266.esp8266.d1_mini/fan_controller.ino.elf 0x40201588 0x40203f2c   # addresses from the dump
```

### Getting back into setup

- **Automatically:** if the saved network can't be reached at boot, the board tries for 20 s (fans at 100 %), then opens the setup access point for 3 minutes, then restarts and tries again. The access point stays up while a device is joined to it.
- **Double reset:** press RST, then press it again within 10 s. The setup access point opens with the same 3-minute timeout. Unplugging power doesn't count; it must be the RST button.

The timeouts are `CONNECT_TIMEOUT_S` and `PORTAL_TIMEOUT_S` at the top of `fan_controller.ino`.

### MQTT

The board can publish its fan curve and readings to an MQTT broker and take curve changes from it. It stays off until you enter a broker.

**Setup.** On the [status page](#status-page), open **MQTT** and enter the broker's IP or DNS name and port (1883 by default). If the broker needs a login, add the user and password. Then press **Save**. The section's title shows the state: `connected`, `not connected (state N)` or `off`. Serial also prints `MQTT: connected to …`. To switch MQTT off, clear the broker field and save.

- **Use an IP or a DNS name.** A `.local` name doesn't work, because the ESP8266 can't resolve mDNS names when it connects out.
- **Password field:** leave it blank to keep the saved password. That only works while the broker and the user stay the same. If you change either, enter the password again, so the old password is never sent to a new broker. Clearing the user removes both.
- **Broker unreachable:** the board tries again after 30 s and doubles the wait after each failure, up to 5 min (`MQTT_RETRY_MIN_S` / `MQTT_RETRY_MAX_S`). Each try can freeze the status page for up to about 6 s. The fans keep running normally. Saving the MQTT form tries again at once, and so does a connection that drops after it was working.

**Topics.** Every topic starts with the board's name, the same `fan-controller-XXXXXX` as on the status page:

| Topic | Direction | Payload |
|---|---|---|
| `…/ramp` | from the board, retained | `{"low":21,"high":30}`: ramp start and end, °C |
| `…/ramp/set` | to the board | `{"low":22,"high":32}`, or one key alone: `{"low":22}` |
| `…/duty` | from the board, retained | `{"min":20,"max":100}`: duty at ramp start and end, % |
| `…/duty/set` | to the board | `{"max":80}` etc. |
| `…/status` | from the board, every 5 s (`MQTT_STATUS_S`) | The same JSON as [`/status.json`](#status-page): `{"t":22.7,"pct":40,"pwr":1,"rpm":[600,630,750],"up":273600,"boots":14,"crashes":1,"reset":"power on"}` |
| `…/online` | from the board, retained | `online`, or `offline` once the board drops off (the broker sends it for the board) |

`ramp` and `duty` are the two rows of the [fan curve](#change-the-fan-curve) form.

**How a set works:**
- **Keys:** a set can carry one key or both. A missing key keeps its current value. Values must be whole numbers.
- **Applied like Save:** the board treats a set exactly like **Save** on the page. The same limits apply, the change takes effect on the next 1 s cycle, and it is stored in flash.
- **Rejected sets:** the board ignores the whole set if any of these is true, and serial prints `MQTT: ignored …`:
  - the result breaks the limits;
  - any key's value isn't a whole number, such as `99.9` or `"32"`;
  - the payload is longer than 127 bytes.
- **Both cases:** the board republishes `ramp` and `duty`, so they always show the curve in force.

**Examples.** `mosquitto_sub` and `mosquitto_pub` come with the `mosquitto` package. Add `-u <user> -P <password>` if the broker needs a login.

```bash
mosquitto_sub -h <broker> -t 'fan-controller-XXXXXX/#' -v      # watch everything
mosquitto_pub -h <broker> -t fan-controller-XXXXXX/ramp/set -m '{"low":22,"high":32}'
mosquitto_pub -h <broker> -t fan-controller-XXXXXX/duty/set -m '{"max":80}'
```

- **Don't publish sets as retained.** The broker would resend them every time the board reconnects, overwriting any change made on the page since.
- **Don't automate sets every few seconds.** Each accepted set that changes the curve rewrites the board's flash. Changes by hand, or an occasional automation, are fine. A set that changes nothing writes nothing.

**Test broker.** If you don't have a broker, `mqtt-broker/` builds a throwaway Mosquitto 2.0.22 in Docker. It uses plain TCP and keeps nothing between runs, retained messages included.

```bash
docker build -t fan-mqtt mqtt-broker
docker run --rm --name fan-mqtt -p 1883:1883 fan-mqtt                                     # no login
docker run --rm --name fan-mqtt -p 1883:1883 -e MQTT_USER=fan -e MQTT_PASS=secret fan-mqtt   # or: login required
docker exec fan-mqtt mosquitto_sub -t 'fan-controller-XXXXXX/#' -v                        # watch; add -u fan -P secret with a login
docker exec fan-mqtt mosquitto_pub -t fan-controller-XXXXXX/duty/set -m '{"max":80}'
```

On the status page, enter your PC's LAN IP as the broker (`ip -4 addr`), not `localhost`. The board connects to the PC from outside, so a firewall on the PC must allow TCP 1883. The `docker run` window logs each connection, e.g. `New client connected … as fan-controller-XXXXXX`, and each refused login (`not authorised`). Ctrl+C stops the broker.

### Security

- `AP_PASS` is committed in the source, so change it before flashing if the repo is shared. It must be at least 8 characters.
- The status and Wi-Fi pages on your LAN have no login. Anyone on your network can open them, change the fan curve, change or erase the Wi-Fi settings, and flash new firmware.
- MQTT is plain TCP, without TLS, and the broker password is stored unencrypted in the board's flash. Anyone who can publish to the broker can change the fan curve.

## Troubleshooting

| Symptom | Likely cause / fix |
|---|---|
| `Permission denied: /dev/ttyUSB0` | Not in `uucp` group yet. Run the `usermod` command from Setup, then log out and back in |
| Board missing from `board list` | Charge-only USB cable; check `dmesg -w` while plugging in (expect `ch341` or `cp210x`). If `brltty` is installed it can grab CH340 adapters: `sudo pacman -Rns brltty` |
| `Timed out waiting for packet header` | Lower upload speed (`baud=115200`). If it persists, hold FLASH and tap RESET to enter the bootloader manually |
| `Port busy` / upload fails right away | Serial monitor still open; close it |
| Board doesn't boot with hardware attached | GPIO15 pulled high (fan wired directly instead of through a transistor), or GPIO0/GPIO2 held low |
| Fans always at 100 % | Sensor not found (`-127 °C` in the log): check the DS1820 wiring and 4.7 kΩ pull-up. Also check whether a fan is wired directly without a transistor: then the PWM is not inverted and `setFan()` needs `analogWrite(pin, pct * 255 / 100)` |
| Occasional single `-127 °C` reading, fans jump to 100 % for a second | The firmware already retries a failed read once, because web traffic can disturb 1-Wire timing on the ESP8266. If it still shows up, check the DS1820 wiring, the 4.7 kΩ pull-up and the cable length |
| RPM reads 0 | Missing tach pull-up, fan not powered, or grounds not common. Expected while the 12 V is switched off (status page says `fans off`) |
| Fans still spin at 0 % | The 12 V is cut only once the temperature is 0.5 °C below where the duty leaves 0 %, and then after 10 s, so wait. If the status says `fans off` and they still spin, the P-MOSFET is probably reversed: its built-in diode then passes 12 V all the time. Source goes to the 12 V supply, drain to the fans |
| Fans never spin, even at 100 % | No 12 V reaches pin 2. Check that D0 measures 3.3 V while the firmware runs (about 1.5 V with the board in reset, where only the 10 kΩ pull-up holds it), the transistor pinouts (they differ between part numbers), and that the NPN emitter is grounded |
| RPM jumps around | Add a 10 kΩ external pull-up (instead of `INPUT_PULLUP`) and/or 10 nF from tach pin to GND |
| A fan reads ~760,000 RPM | Its tach pin is counting the 25 kHz PWM (760,000 ÷ 30 ≈ 25,000 pulses/s), so it's shorted to a PWM line. Look for a solder bridge between neighbouring header pins (D5 sits next to D6 on the D1 mini) or a tach wire touching a transistor collector (fan pin 4). If unplugging the fan doesn't change the reading, the short is on the board |
| Wi-Fi flaky or won't connect | A tach pin shorted to PWM (row above) fires 25,000 interrupts per second and starves Wi-Fi. Fix that first |
| Setup access point appears unexpectedly | A second reset within 10 s of boot counted as a [double reset](#getting-back-into-setup). Opening the serial monitor right after flashing can do this. Press RST once and wait |
| `crashes` keeps going up | Leave a serial monitor running until it happens again, then [decode the stack dump](#uptime-boots-and-crashes). A `hardware watchdog` crash prints no dump |
| `last reset: power on`, but nobody switched it off | The board lost power. Check its 5 V supply and USB cable |
| `fan-controller-XXXXXX.local` doesn't resolve | Check the chip ID first: `avahi-browse -rt _http._tcp` or your router's DHCP list shows each board's name. Otherwise `avahi-daemon` usually isn't running (`systemctl is-active avahi-daemon`). See [Setup step 5](#5-resolve-local-names). If it runs and still fails, a firewall may be blocking UDP 5353. Or use the IP from serial |
| Changed `DEFAULT_CURVE` and flashed, but the curve didn't change | A curve saved from the status page takes priority over the compiled defaults. Press **Defaults** on the page |
| MQTT says `not connected (state -2)` or `(state -4)` | The board can't reach the broker, or it didn't answer in time. Check the IP and port, that the broker is running, and that no firewall blocks the port (1883). A `.local` broker name never works here: use the IP |
| MQTT says `not connected (state 4)` or `(state 5)` | The broker refused the login. Re-enter the user and password (the password field is always shown blank) |
| An MQTT set changes nothing | Serial prints `MQTT: ignored …`. The values broke the [curve limits](#change-the-fan-curve), a value isn't a whole number, or the payload isn't JSON like `{"low":22}`. To move the ramp start past its current end, send both in one message: `{"low":35,"high":40}` |
| Status page unreachable after changing network | The board couldn't join the new network (wrong password, or out of range). Press RST: if the saved network still can't be reached, it falls back to the setup access point after 20 s |

or passes `-b $FQBN` and `-p $PORT` explicitly.

`git_hash.h` is ignored because `./build.sh` regenerates it on every build, and a commit can't contain its own hash.
